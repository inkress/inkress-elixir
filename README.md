# Inkress

A thin, idiomatic Elixir wrapper for the [Inkress](https://inkress.com) API.

Scope is deliberately small:

- **Create orders** — `Inkress.Orders.create/2` (`POST /api/v1/orders`)
- **Create payment links** — `Inkress.PaymentLinks.create/2` (`POST /api/v1/payment_links`), the
  server-side checkout primitive: create a link, send the customer to its hosted pay page
- **Read products** — `Inkress.Products.list/2` + `find_by_data/3` (map an external id to a product)
- **Verify webhooks** — `Inkress.Webhooks.verify/2` (checks the signed webhook JWT and hands
  you a typed event, with accessors that work across both wire shapes)

Everything returns idiomatic `{:ok, _}` / `{:error, _}` tuples. No global state, no
config files required — you pass an explicit client.

## Installation

```elixir
# mix.exs
def deps do
  [
    {:inkress, "~> 0.2"}
  ]
end
```

> **Elixir 1.15+ required.** The secure `hpax` release (the one that fixes the HIGH
> HPACK-DoS advisory) needs Elixir `~> 1.15`, and Finch depends on it. The same
> OTP 26 as older projects works fine — only the Elixir minor needs to be ≥ 1.15.

The library starts its own Finch pool (`Inkress.Finch`) under its supervision tree,
so there's nothing to wire up. To reuse a pool you already run, see
[Custom HTTP pool](#custom-http-pool).

## Creating an order

```elixir
client = Inkress.new(api_token: "sk_live_…", merchant_username: "my-store")

{:ok, order} =
  Inkress.Orders.create(client, %{
    currency_code: "JMD",
    total: 2999,
    customer: %{email: "jane@example.com", first_name: "Jane", last_name: "Doe"},
    products: [%{id: 1, quantity: 2}],
    data: %{shipping_address: %{city: "Kingston", country: "JM"}}
  })

order.id            #=> 42
order.reference_id  #=> "ref_456"  (auto-generated by Inkress when you omit it)
order.raw           #=> the full decoded order map
```

`kind` defaults to `"online"` (the API rejects `"order"`; valid kinds are
online/payment_link/cart/invoice/subscription/offline). `currency_code` is required. Params
use atom keys. `Inkress.create_order/2` is a convenience alias.

### Order-create as checkout (redirect the customer to pay)

`POST /orders` returns a hosted pay URL, so you can create the order server-side and send the
buyer there — no separate payment link needed:

```elixir
{:ok, order} =
  Inkress.Orders.create(client, %{
    currency_code: "JMD",
    reference_id: "4821",                                   # echoed back on the webhook
    customer: %{email: "jane@example.com", first_name: "Jane", last_name: "Doe"},
    products: [%{id: 164, quantity: 1, unit_price: 33_600}] # the service, priced by the quote
  })

redirect_to(Inkress.Order.pay_url(order))   # invoice_url → payment_urls.payment_url → short_link
```

For a quote with no catalog line, use an open-amount order (`total` + `title`) instead of
`products`. Per-currency minimums apply (e.g. JMD $150).

### Reading products (map an external id → a product)

```elixir
{:ok, products} = Inkress.Products.list(client, %{page_size: 100})
# products carry their `data` map, so you can resolve by a key you stored there:
Inkress.Products.find_by_data(products, "curator_post_id", "7447282")  #=> %Inkress.Product{id: 164}
```

On failure you get a normalized error:

```elixir
{:error, %Inkress.Error{status: 422, message: "currency_code is required", details: %{…}}}
```

### Open-amount orders

To charge an arbitrary amount with no catalog products (a quoted price, a service,
a custom invoice amount), use `create_open_amount/2` — it requires a positive `:total`,
rejects `:products`, and validates before any request:

```elixir
{:ok, order} =
  Inkress.Orders.create_open_amount(client, %{
    currency_code: "JMD",
    total: 5000,
    title: "Consulting — 2h",
    customer: %{email: "jane@example.com"}
  })
```

### Custom / quoted pricing

To set an explicit per-line price (dynamic or quoted pricing — above **or** below
catalog), add `unit_price` to a product line. This is honored **only** when the client
is built with a **secret key** (`sk_live_…` / `sk_test_`) — a server-side-only concern;
publishable or customer tokens fall back to catalog pricing.

```elixir
client = Inkress.new(api_token: "sk_live_…", merchant_username: "my-store")

{:ok, order} =
  Inkress.Orders.create(client, %{
    currency_code: "JMD",
    customer: %{email: "a@b.com", first_name: "Jane", last_name: "Doe"},
    products: [%{id: 1, quantity: 2, unit_price: 13_700}]  # server re-prices this line to 13_700
  })
```

Omit `unit_price` (or use a non-secret token) and the line is priced from the catalog as
usual. See `docs/custom-pricing-design.md` for the design and trust model.

## Creating a payment link (server-side checkout)

A payment link is created server-side and paid by the customer on Inkress's hosted page
(`…/p/<uid>`), where the browser supplies the fraud/3-DS context. Prefer this over a
checkout *session* for server-to-server flows — a session runs the risk gate at creation
and needs a browser risk reference, so a bare server call is declined.

```elixir
client = Inkress.new(api_token: "sk_live_…", merchant_username: "nkc")

{:ok, link} =
  Inkress.PaymentLinks.create(client, %{
    title: "Invoice #4821 — Deep Cleaning",
    total: 33_600,                # omit for a customer-entered amount
    currency_code: "JMD",         # or currency_id: 1
    reference_id: "4821",         # mirrored into data.reference_id; comes back on the webhook
    data: %{redirect_url: "https://newkingstoncleaning.com/thanks"}
  })

redirect_to(Inkress.PaymentLinks.pay_url(client, link.uid))   #=> https://inkress.com/p/<uid>
```

Payment links have no native `reference_id` column, so pass `:reference_id` (it is mirrored
into `data.reference_id`) and, if you reconcile off the flat webhook, encode it in `:title`
too. When the customer pays, Inkress creates the order and sends an `orders.<status>` webhook.
`Inkress.create_payment_link/2` is a convenience alias.

## Verifying a webhook

Inkress signs webhooks as an HS256 JWT (the JWT's claims *are* the event) and delivers
them in two shapes the SDK normalises for you:

- **Modern** — an envelope keyed by `"event"` (e.g. `"orders.paid"`) with the order under `"order"`.
- **Flat (provider/facilitator)** — top-level `"status"`, `"reference"`, `"amount"`,
  `"card_suffix"`, `"client"`, `"title"` (this is what current provider/hosted-checkout
  webhooks deliver, as a `jwt` form param).

`verify/2` checks the signature and returns a typed event — no client needed. Use the
**accessor functions** (`status/1`, `reference/1`, `amount/1`, `customer_email/1`,
`card_last4/1`, `order/1`, `title/1`) so your handler works regardless of shape:

```elixir
# In a Plug/Phoenix controller
signature = conn |> Plug.Conn.get_req_header("x-inkress-signature") |> List.first()

alias Inkress.Webhook.Event

case Inkress.Webhooks.verify(signature, webhook_secret) do
  {:ok, %Event{type: :order_paid} = event} ->
    fulfill_order(
      reference: Event.reference(event),      # your reference_id
      amount:    Event.amount(event),
      email:     Event.customer_email(event),
      last4:     Event.card_last4(event)
    )
    Plug.Conn.send_resp(conn, 200, "")

  {:ok, %Event{type: :merchant_registered, raw: raw}} ->
    store_api_credentials(raw["secret_key"], raw["public_key"])
    Plug.Conn.send_resp(conn, 200, "")

  {:ok, _other} ->
    Plug.Conn.send_resp(conn, 200, "")

  {:error, reason} ->
    # :invalid_signature | :malformed | :missing_secret
    Plug.Conn.send_resp(conn, 400, to_string(reason))
end
```

`Inkress.verify_webhook/2` is a convenience alias. The current provider webhook is
delivered as a `jwt` form field, so read it with `conn.params["jwt"]` where that applies;
the modern webhook uses the `x-inkress-signature` header. Either way, pass the JWT string
to `verify/2`.

### Event types

`event.type` is a stable atom parsed from either shape (unrecognised or type-less payloads
resolve to `:unknown`, never an error). Order events are `orders.<status>` on the wire and
map to `:order_<status>`:

`:merchant_registered`, `:order_created`, `:order_paid`, `:order_pending`, `:order_failed`,
`:order_cancelled`, `:order_refunded`, `:order_prepared`, `:order_shipped`, `:order_delivered`,
`:order_completed`, `:order_returned`, `:order_verifying`, `:payment_authorized`,
`:payment_captured`, `:payment_failed`, `:payment_link_visited`, `:subscription_created`,
`:subscription_cancelled`.

Prefer the accessors (`Event.status/1`, `reference/1`, `amount/1`, `customer_email/1`,
`card_last4/1`, `order/1`, `title/1`) over reaching into `event.data`/`event.raw` — they
read the right place for both wire shapes. The full event is always under `event.raw`.

## Configuration

`Inkress.new/1` options:

| Option              | Default              | Notes                                             |
| ------------------- | -------------------- | ------------------------------------------------- |
| `:api_token`        | — (required)         | Bearer token                                      |
| `:merchant_username`| — (required)         | Sent as `Client-Id: m-<username>`                 |
| `:mode`             | `:live`              | `:live` or `:sandbox` (selects the base URL)      |
| `:base_url`         | derived from `:mode` | Override, e.g. `http://localhost:4000` for dev    |
| `:finch`            | `Inkress.Finch`      | Finch pool name                                   |
| `:receive_timeout`  | `30_000`             | Per-request receive timeout (ms)                  |
| `:http_client`      | `Inkress.HTTPClient.Finch` | Any module implementing `Inkress.HTTPClient` |

Base URLs: `:live` → `https://api.inkress.com`, `:sandbox` → `https://api-dev.inkress.com`.

### Custom HTTP pool

```elixir
# your supervision tree
children = [{Finch, name: MyApp.Finch}]

client = Inkress.new(api_token: "…", merchant_username: "…", finch: MyApp.Finch)
```

The transport is a behaviour (`Inkress.HTTPClient`), so you can also supply your own
adapter via `:http_client` — useful for tests or to route through a different client.
